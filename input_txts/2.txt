Подход к автоматизации деловых процессов научной организации. Часть 2. Обеспечение информационной безопасности
Акимова Г.П., Даниленко А.Ю., Пашкина Е.В., Пашкин М.А., Подрабинович А.А., Соловьев А.В., Туманова И.В.
ИСА ФИЦ ИУ РАН
Введение
Данная статья продолжает начатый в [1] цикл работ, посвященный автоматизации деловых процессов научной организации. В первой статье цикла рассмотрены общие проблемы, возникающие при цифровизации не отдельных видов деятельности предприятия, а всей его жизни, т.е. всех деловых процессов, включая их взаимодействие. Основная сложность при решении этой задачи состоит в объединении программного обеспечения, используемого в организации, в единый программный комплекс для обеспечения автоматизации деловых процессов, в которых участвуют различные действующие информационные системы предприятия, решающие, порой, не связанные между собой задачи и созданные независимыми коллективами разработчиков.
Отдельно в [1] рассмотрены особенности трудовой деятельности научных коллективов, для которых характерны работа с информацией различного уровня конфиденциальности, в том числе с секретными данными, большое число участвующих сотрудников, использование различных прикладных программ, в том числе текстовых процессоров, программ для подготовки презентаций и различных иллюстраций, активное использование Интернет. По сути, в данном случае автоматизации подлежит творческая деятельность: изучение внешних источников информации, подготовка статей и отчетов, общение с коллегами из других организаций и государств, участие в Скайп конференциях и вебинарах. Однако, помимо творческой составляющей в любой организации имеется и организационная, которая тоже нуждается в автоматизации. Это касается подготовки различных заявлений, служебных записок, отчетов, контроля исполнения работ и пр.
Для решения указанных задач в [1] предлагается разработка и внедрение новой информационной системы, которая объединит все работающие в настоящее время, а также перспективные, программы в единый программный комплекс. При таком решении потребуется доработка имеющихся систем для совместной работы только с одной объединяющей информационной системой. В качестве такой объединяющей системы целесообразно использовать систему обмена информацией, внедрение которой позволит организовать тесное взаимодействие сотрудников, надежную передачу документов и данных между подразделениями, а также, в ряде случаев, постановку задач с контролем их исполнения (в пределе поставленную задачу может решать система электронного документооборота (СЭД) предприятия). При этом необходимо отметить, что внедрение предлагаемой комплексной системы управления (КСУ) возможно только в случае решения целого ряда задач, связанных с обеспечением информационной безопасности, возможным путям решения которых, а также возникающих при этом проблем посвящена данная статья.
Информационные объекты
Все автоматизированные информационные системы (АИС) работают с наборами данных, которые формируются и обрабатываются по правилам, определяемым функционалом этих АИС. В большинстве систем эти наборы данных хранятся в базах данных (БД), причем каждый из них может представляться большим числом записей в различных таблицах. В таких случаях обычно говорят об информационных объектах, имея в виду, что каждый такой объект представляет собой некую самодостаточную сущность, например, электронный документ в случае системы электронного документооборота, платежная ведомость или счет-фактура для бухгалтерских систем, личное дело, больничный лист, заявление на отпуск для кадровых систем. Эти наборы данных специфичны для каждой прикладной АИС, однако если говорить о разработке и внедрении КСУ, то потребуется формализовать понятие информационного объекта с целью обеспечения работы КСУ с информацией всех подключенных к ней внешних систем. 
Ниже перечислены основные требования, которым должны удовлетворять такие информационные объекты (объекты КСУ):
    • объект создается, редактируется и уничтожается прикладной АИС, но при этом ряд его свойств обрабатывается КСУ;
    • информационный объект хранится в собственной БД создавшей его АИС;
    • существует программа, которая преобразует информационный объект в файл для контроля целостности и передачи в другие информационные системы с помощью КСУ. Это может быть прикладная АИС, которая его создает, хранит и обрабатывает. Однако для полноценного контроля целостности в ходе перемещения его между различными АИС потребуется программный модуль, входящий в состав программного обеспечения КСУ для выполнения подобного преобразования;
    • показ пользователям объекта средствами КСУ не требуется, это делается прикладной АИС, работающей с данным объектом;
    • информационный объект обладает обязательным набором реквизитов, которые могут обрабатываться КСУ в процессе передачи между прикладными системами. Этот набор может включать:
        ? идентификатор АИС, создавшей объект;
        ? внутренний идентификатор объекта в БД создавшей его АИС;
        ? краткое человекочитаемое описание объекта или его наименование, которое может потребоваться для протоколирования действий с объектом в протоколе безопасности;
        ? метка целостности объекта;
        ? список доступа объекта (разрешения и запреты) для реализации дискреционного контроля доступа;
        ? мандатный профиль объекта для реализации мандатного контроля;
        ? электронная подпись (ЭП) объекта с указанием идентификаторов подписавшего пользователя и открытого ключа для проверки подписи (в случае использования усиленной ЭП).
Сразу отметим, что вопросы идентификации пользователей для списков доступа и ЭП будут рассмотрены в следующих разделах настоящей статьи. 
Учетные записи пользователей
Все работающие в организации информационные системы коллективного пользования имеют свои базы данных учетных записей зарегистрированных пользователей. Помимо этого, существует общая база данных всех сотрудников – база домена (Active Directory в случае применения в организации операционной системы (ОС) Windows), которая используется для идентификации и аутентификации сотрудников при входе в домен, а также для предоставления прав на действия в файловой системе, в том числе для управления доступом к общим корпоративным ресурсам. Для случая систем индивидуального пользования, таких как текстовые процессоры, базы данных пользователей не создаются, права на доступ к этим системам не проверяются, а права доступа к создаваемым или модифицируемым ими информационным объектам регулируются на уровне файловых систем пользовательских компьютеров и домена. 
В случае внедрения КСУ появляется возможность реализовать единый подход к регистрации пользователей с последующей реализацией единой политики управления доступом. Для этого целесообразно создать базу данных учетных записей на основе Active Directory или другой базы данных домена ОС. При этом не обязательно создавать новую базу данных на отдельном компьютере, можно использовать имеющуюся базу домена, дописав в нее дополнительную информацию об учетных записях, в частности, в нее могут быть занесены данные о доступных пользователю уровнях конфиденциальности сеансов работы в КСУ или об уровнях конфиденциальности документов, с которыми пользователь может работать.
Для полноценного функционирования КСУ БД ее пользователей должна содержать информацию о пользовательских группах таких, как структура подразделений организации с учетом их иерархии, группы доступа, списки рассылки и т.д. Должны храниться данные о ролях и пользователях, назначенных на эти роли, пользовательских привилегиях. В связи с этим вопрос о формировании отдельной БД пользователей или об использовании БД домена должен решаться при проектировании конкретной КСУ с учетом объема данных, которые необходимо хранить в этой БД.
В отличие от большинства организаций сотрудники научных коллективов могут входить в несколько подразделений, причем это не отклонение от правил, а именно норма. Помимо подразделений в обычной иерархии – отделения, отделы, лаборатории, сектора и т.д., сотрудники могут входить в редакционные подразделения, ученые и диссертационные советы, подразделения, создаваемые для выполнения конкретных проектов и т.д. Эта особенность должна учитываться при проектировании БД пользователей КСУ, назначении прав доступа к информационным объектам как КСУ, так и прикладных АИС. Особое значение имеет эта особенность при реализации процедуры удаления учетной записи пользователя, т.к. ее удаление из одного подразделения не должно приводить к удалению из всей БД, что не исключает возможность и полного удаления всех данных пользователя из БД.
Управление доступом
В каждой из работающих в организации АИС имеются свои правила разграничения доступа к собственным информационным объектам, при этом используются свои базы данных пользователей, учетные записи в которых также формируются средствами прикладной АИС. В случае, если требуется передать данные между различными системами формируется пакет данных в формате, поддерживаемом обеими АИС, который по каналам связи или на внешнем носителе информации передается между системами. Если системы установлены на одном компьютере, передача происходит через файловую систему. Пользователи, выполняющие передачу информации, должны иметь определенные полномочия в каждой АИС, а именно, в системе, отправляющей данные, право на экспорт информационных объектов, а в принимающей на создание новых объектов либо на импорт объектов, экспортированных из внешних приложений (это может быть отдельное право, не зависящее от права на создание новых объектов). Корректность всех действий в каждой системе обеспечивается организационными мерами. Протоколирование действий по передаче информации при такой логике работы выполняется в каждой АИС независимо. В случае, если передаваемые данные относятся к категории конфиденциальных, согласование уровней конфиденциальности во всех системах также обеспечивается пользователями, выполняющими обмен информацией.
Такая логика работы может быть сохранена в случае внедрения КСУ, однако это не позволит использовать все ее возможности. Если передаваемая информация оформляется в виде объектов КСУ, то может быть реализована единая система управления доступом в рамках всей организации, по крайней мере для пользователей, зарегистрированных в БД домена. Для объектов КСУ списки доступа наиболее целесообразно формировать с использованием идентификаторов единой базы данных организации. Такой подход позволяет автоматизировать назначение прав при передаче информации между разными системами, т.к. права на объект КСУ в принимающей системе пользователь, имеющий их в отправляющей, получит автоматически. В случае же передачи объекта другому пользователю в той же или в другой АИС достаточно просто дать ему необходимые права, которые автоматически преобразуются в права в принимающей системе. Разумеется, такое назначение прав может быть выполнено только пользователем, имеющим право модификации прав доступа для данного информационного объекта с точки зрения деловой логики отправляющей системы. Отдельной проработки требует описанный алгоритм в том случае, если пользователь, получающий объект в принимающей системе, должен иметь возможность его редактирования, а в отправляющей он не имеет прав даже на его чтение, т.е. права на конкретный информационный объект в обеих АИС, участвующих в обмене информацией, существенно различаются. В этом случае целесообразно при назначении прав доступа указывать также АИС, в которой эти права действуют. Для облегчения работы сотрудников в таких ситуациях целесообразно использовать стандартизованные маршруты движения документов и других информационных объектов КСУ, в которых указываются АИС, пользователи, их права, а также подразделения, в которые следует доставить информацию.
Описанная логика реализации дискреционного управления доступом может быть дополнена рядом полезных возможностей. Так, целесообразно предоставлять доступ к объектам КСУ не только конкретным пользователям, но и группам пользователей, а также ролям, на которые может быть назначен какой-либо сотрудник. Права доступа могут предоставляться с учетом положения сотрудника в должностной иерархии, например, руководитель подразделения может иметь право чтения, редактирования, а также модификации прав доступа информационных объектов своего подразделения, т.е. объектов, созданных или доступных для чтения его сотрудникам, включая подчиненные подразделения. В этом контексте может быть использовано и понятие привилегии, которой присваивается фиксированный набор прав, в дальнейшем эта привилегия может быть присвоена пользователю или группе пользователей. На этом механизме может быть реализовано предоставление прав на документы, обрабатываемые СЭД, делопроизводителям подразделений. В частности, делопроизводителям могут быть предоставлены права на чтение всех регистрационных данных документов подразделения и на изменение прав доступа, а возможности читать сами электронные документы они могут не иметь.
Для научных предприятий при проектировании и реализации политики управления доступом следует избегать предоставления прав на информационные объекты по формальным должностям (программист, научный сотрудник, ведущий специалист и т.д.), а также по ученым степеням или званиям (кандидат или доктор наук, доцент, профессор). Доступ ко всем объектам всех АИС, работающих в организации, должен предоставляться только в зависимости от служебных обязанностей сотрудников.
Согласно действующей нормативной базе (см, например, [2]), в АИС требуется «реализация необходимых методов (дискреционный, мандатный, ролевой или иной метод), типов (чтение, запись, выполнение или иной тип) и правил разграничения доступа», в частности, для работы с данными высокого уровня конфиденциальности может требоваться реализация мандатного разграничения [3]. Согласно этому документу для средств вычислительной техники (СВТ) четвертого класса защищенности: «Для реализации этого принципа (мандатного принципа разграничения доступа) должны сопоставляться классификационные метки каждого субъекта и каждого объекта, отражающие их место в соответствующей иерархии. Посредством этих меток субъектам и объектам должны назначаться классификационные уровни (уровни уязвимости, категории секретности и т.п.), являющиеся комбинациями иерархических и неиерархических категорий». Однако, как показывает практика, применение данного пункта в полном объеме ведет к логическим сложностям в реализации и последующем использовании алгоритмов обработки нескольких иерархических и неиерархических категорий, поэтому при реализации КСУ следует рассмотреть единственную возможность обработки одной иерархической категории – степени конфиденциальности информации и, соответственно, уровня пользователя в этой иерархии. Уровень пользователя должен соответствовать выполняемой им работе и не может, как и в случае дискреционного разграничения, напрямую зависеть от должности или ученой степени.
Мандатный метод разграничения доступа в любой АИС может быть реализован следующими тремя способами. Прежде всего данные разного уровня конфиденциальности могут быть разделены физически, т.е. обрабатываться в разных контурах локальной вычислительной сети, храниться на разных серверных компьютерах, доступ к ним осуществляется с разных клиентских рабочих мест. В этом случае в рамках АИС или КСУ не требуется предусматривать каких-либо программных механизмов мандатного разграничения. 
Второй способ состоит в обработке данных всех уровней конфиденциальности на одних и тех же компьютерах с получением информации об этих уровнях от используемой ОС. При этом предполагается, что ОС предусматривает создание сеансов работы пользователей с разными уровнями конфиденциальности, и этот уровень выбирается пользователем при входе в домен. В этом случае прикладная АИС при запуске клиентского приложения получает уровень конфиденциальности сеанса и использует его при дальнейшей работе для разграничения доступа к своим информационным объектам, в том числе к объектам КСУ.
В третьем варианте мандатное разграничение доступа полностью реализуется средствами АИС. Это означает, что при входе пользователя в домен его сеансу работы присваивается максимальный уровень конфиденциальности, доступный в домене, а реальный уровень конфиденциальности, определяющий его права на действия с информационными объектами, выбирается им при работе в прикладной АИС. Такой подход предоставляет широкие возможности для различных действий с уровнями конфиденциальности информации, например, при создании информационного объекта пользователь может сам указать его уровень конфиденциальности, отличный от уровня его сеанса работы. Однако, реализация такой логики достаточно сложна алгоритмически, что ведет к усложнению процедуры сертификации программного обеспечения.
Помимо рассмотренных выше действий с информационными объектами таких, как создание, чтение и редактирование, существуют уничтожение информационного объекта и модификация прав доступа. Во многих системах, в первую очередь в СЭД, уничтожение объекта, в данном случае электронного документа, рассматривается как исключительное событие, все документы должны храниться либо в самой СЭД, либо в специально созданном архиве электронных документов, работающем совместно с СЭД. Однако, в случае произвольной АИС такие требования могут и не предъявляться, уничтожение рабочего материала может быть обычным действием. 
В случае, когда информационный объект уничтожается его создателем вскоре после создания, причем с этими данными не ознакомился никто другой, это действие не вызывает особых вопросов. Ситуация существенно изменяется, когда информационный объект был передан в другие АИС, с ним работает несколько сотрудников. В этом случае процедура уничтожения объекта, даже если это рабочий материал, не зарегистрированный в качестве полноценного электронного документа, должна быть детально проработана как с точки зрения пользователя, имеющего право на инициализацию процесса уничтожения, так и алгоритма действий сотрудников, работающих с этими данными. Отдельно прорабатывается последовательность действий во внешних системах, которые работают с уничтожаемым объектом. Понятно, что наиболее полно и непротиворечиво все указанные действия могут быть реализованы только в случае внедрения в организации КСУ.
Администрирование комплексной системы
Любой программный комплекс, любая АИС нуждаются в квалифицированном администрировании. Для их нормального функционирования необходимо наличие технического подразделения, поддерживающего работу (в пределе одного или двух системных администраторов). В случае, когда в АИС обрабатываются конфиденциальные данные, требуется наличие администратора безопасности (начиная с уровня 1В по Руководящему документу [4]).  В связи с тем, что в КСУ управление учетными записями пользователей целесообразно реализовывать на уровне всей организации, вне конкретных АИС, наиболее логично вывести администрирование средств защиты информации за рамки конкретных информационных систем, введя общесистемную роль администраторов безопасности КСУ или всей организации в целом. Точно также управление правами доступа к объектам КСУ, как отмечалось ранее, должно выполняться на уровне КСУ, а не конкретных систем.
Управление правами доступа к информационным объектам при их перемещении между различными системами и пользователями, работающими с этими объектами, целесообразно осуществлять с использованием маршрутов, создаваемых на основе заранее заданных шаблонов. Формирование таких шаблонов представляет собой достаточно сложную задачу, которую должны решать администраторы безопасности совместно с представителями функционального подразделения. Однако, проверять и вводить в действие новые шаблоны должны администраторы безопасности, поскольку именно они отвечают за политику безопасности.
Для научных организаций характерно большое разнообразие маршрутов, для которых требуется разработка шаблонов. Это ведет к необходимости понимания специфики работы многочисленных подразделений администраторами безопасности, которые не должны полностью полагаться на результаты работы представителей функциональных подразделений.
Особенности применения средств защиты информации
В случае внедрения в организации КСУ должны быть выполнены все обычные требования к аппаратным средствам и общему программному обеспечению, предъявляемые в соответствии с уровнем конфиденциальности данных, обрабатываемых в организации. Обычно в таких случаях требуются аппаратно-программные модули доверенной загрузки (АПМДЗ), а также доверенные ОС и СУБД, прошедшие сертификацию для работы с информацией требуемого уровня конфиденциальности. В ряде случаев для обеспечения доверенной загрузки операционной системы требуется проверка БИОС на всех серверных и клиентских компьютерах. На всех компьютерах должны быть установлены средства, обеспечивающие установку только разрешенного программного обеспечения, возможно применение программного или аппаратного шифрования сетевого трафика в локальной сети, защита каналов связи за пределами контролируемой зоны в данной работе не рассматривается. Необходимость применения перечисленных средств защиты информации (СЗИ) и требования к их реализации определяются степенью конфиденциальности обрабатываемых данных, а также моделями вероятных угроз и нарушителей.
Ранее были рассмотрены несколько СЗИ, которые должны встраиваться в любую АИС, в том числе и в КСУ: идентификация, аутентификация и управление доступом по дискреционной, ролевой и мандатной моделям. К категории встраиваемых СЗИ можно отнести протоколирование, оповещения и блокировки, а также в средства работы с электронной подписью, которые обычно относят к СЗИ.
Протоколирование событий безопасности, в том числе действий с объектами защиты, начало и завершение сеансов работы пользователей, должно быть реализовано в рамках прикладной АИС, поскольку только в ней доступна необходимая информация. В случае внедрения КСУ, обеспечивающей взаимодействие всех АИС организации, следует рассмотреть вопрос ведения протоколов безопасности в части именно совместной работы различных систем. Если при передаче данных между системами какое-либо действие будет зафиксировано в двух протоколах: в одном экспорт данных, а в другом импорт, то в дальнейшем окажется весьма сложно установить, что же именно произошло, поскольку в этих системах объект будет иметь разные идентификаторы, разные названия и прочие идентифицирующие признаки. Тем более, если какой-либо объект КСУ будет перемещаться между несколькими системами по достаточно сложному маршруту, то восстановить историю работы с ним окажется затруднительно. Протоколирование же межсистемного взаимодействия и ведение единого протокола безопасности организации средствами КСУ позволит решить указанную проблему. Отметим, что в протокол безопасности заносятся и события, связанные с изменениями в базе данных пользователей: создание новых учетных записей, удаление устаревших, изменение прав пользователей, создание, удаление и изменение состава групп пользователей. Поскольку, как отмечалось ранее, эти действия выполняются на уровне общей БД пользователей КСУ, их протоколирование также должно выполняться с помощью ее механизмов.
С обработкой событий безопасности связаны и средства оповещения административного персонала о событиях, требующих немедленного реагирования, а также блокировки информационных объектов и учетных записей пользователей. Эти действия также должны быть реализованы в рамках КСУ, в ее составе целесообразно реализовать АРМ администратора безопасности, на который выводятся оповещения, для последующей возможности установки и снятия блокировки как информационных объектов, так и пользователей. 
В рамках предложенного в статье подхода, работа с электронными подписями и контроль целостности информационных объектов должны быть реализованы средствами КСУ. Контроль целостности может быть реализован путем вычисления хэш-значений информационных объектов, хранения полученных хэш-значений в отдельной БД под управлением КСУ и проверки целостности по команде пользователей или автоматически в каких-либо критичных ситуациях, например, при импорте объекта КСУ, экспортированного из какой-либо АИС. Что касается электронных подписей, то для полноценного внедрения усиленных ЭП [5] требуется организация ключевой инфраструктуры, обеспечивающей хранение закрытых ключей пользователей, а также доступ к открытым ключам для проверки подписей. Все эти действия, а также регулярная замена криптографических ключей, наиболее естественно реализуются с помощью механизмов, встроенных в КСУ. Отметим, что в рамках единой системы, которой и является КСУ, может с успехом использоваться и простая ЭП, которая «посредством использования кодов, паролей или иных средств подтверждает факт формирования электронной подписи определенным лицом» [5, 6].
Как отмечено в [1], одной из особенностей научной организации является регулярная работа с архивными материалами, при этом под архивом понимается не столько делопроизводственный архив, сколько научная библиотека, в которой хранятся статьи, отчеты, журналы по тематике организации, причем зачастую они могут содержать конфиденциальную информацию, ознакомление с которой допускается по отдельному разрешению руководства. Для автоматизации доступа к таким архивам может с успехом использоваться КСУ, обладающая функционалом СЭД. В этом случае можно рекомендовать следующий алгоритм:
    1. сотрудник, которому требуется ознакомиться с архивным материалом, отправляет запрос сотруднику, который правомочен принимать решение о допуске к требуемой информации. В реальности в организации может быть достаточно много архивов, их владельцев, а также алгоритмов получения разрешений, согласованных несколькими сотрудниками. Для автоматизации таких процессов можно использовать маршруты движения запросов, причем шаблон такого маршрута может быть свойством конкретного материала. В этом случае пользователь находит необходимую информацию по каталогу и запускает процесс согласования своего допуска, предварительно обосновав необходимость получения такой информации;
    2. после согласования запроса электронная копия материалов в виде файла прикрепляется к документу-запросу, становясь доступной запросившему сотруднику;
    3. запросивший сотрудник знакомится с полученными материалами;
    4. через определенное время, заданное в свойствах исходного архивного материала (например, 1 сутки или 1 неделя), приложенный файл удаляется из документа-запроса, таким образом происходит действие, аналогичное возврату материала, полученного во временное пользование.
Возможна и более простая схема доступа к архиву, здесь приведен один из возможных вариантов его реализации.
Внешний информационный обмен
Как отмечено в [1], «процесс научного поиска невозможен без тесного общения с коллегами как из своего института, так и других организаций». При этом существенно то, что в случае научных коллективов привычные алгоритмы этого общения существенно отличаются от стандартного взаимодействия организаций, подчиняющегося прописанным в законах и инструкциях процедурам. По сложившейся практике обмен документами между организациями идет через секретариаты, особенно это актуально для случая, когда документы содержат конфиденциальные данные. Тем не менее, для случая научных коллективов такая логика работы неизбежно приведет к существенному замедлению совместных работ группы исследователей. В связи с этим целесообразно реализовать средствами КСУ механизм обмена информацией между сотрудниками разных организаций, обеспечивающий требуемый режим сохранения конфиденциальности.
В качестве прототипа такого механизма могут служить СЭД, предназначенные для обмена документами между серверами, расположенными в разных организациях [7], в этом случае при настройке СЭД можно указать состав сотрудников, которые могут получать информацию из внешних организаций, так называемые «контактные лица». Этот подход предполагает ограничение числа сотрудников, которым доступно такое общение.
Если КСУ внедрена в нескольких совместно работающих организациях, с ее помощью можно организовать непосредственное общение сотрудников, в том числе и обмен данными разной степени конфиденциальности. Для исключения утечки конфиденциальной информации помимо очевидных организационных мер в виде персональной ответственности сотрудников целесообразно реализовать детальное категорирование таких сведений по аналогии с перечнями секретных сведений, принятыми в секретном делопроизводстве [8]. В этом случае можно заранее определить, сведения каких категорий могут передаваться в каждую из внешних организаций, с которыми установлено взаимодействие. Для особо чувствительных данных можно рекомендовать предварительную проверку отправляемых средствами КСУ сообщений либо руководителями подразделений, либо специально выделенными сотрудниками или подразделением.
В повседневной жизни для общения широко используются средства обмена мгновенными сообщениями – мессенджеры. В рамках КСУ должна быть учтена возможность реализовать такие программные компоненты, которые можно использовать как внутри организации, так и для внешнего обмена информацией. Однако, в этом случае возникает вопрос соблюдения режима конфиденциальности, что может быть достигнуто как организационными, так и программно-техническими мерами. В частности, обмен мгновенными сообщениями может быть разрешен только между пользователями, работающими в одном и том же режиме конфиденциальности, а внешний обмен контролироваться специально выделенными сотрудниками.
В контексте внешнего информационного обмена возникает также вопрос правил и способов использования открытых каналов связи для работы в сети Интернет и пользования электронной почтой. В [1] делается вывод, что физическое разделение информационных потоков путем работы с открытыми каналами с выделенных компьютеров, сопровождаемое полным запретом переноса данных с этих компьютеров в локальную сеть организации, полностью решает все проблемы информационной безопасности. Однако, такой подход не способствует эффективной работе научного коллектива. Для работы через открытые каналы с компьютеров, обрабатывающих конфиденциальную информацию, можно рекомендовать применение антивирусных средств, а также использование межсетевых экранов на серверах, непосредственно подключенных к этим каналам. 
Программные модули, реализующие функциональность этих экранов, должны быть настроены на пропуск в локальную сеть ограниченного набора данных, т.е. должен быть реализован принцип «запрещено все, что не разрешено», причем разрешение должно быть явным и однозначным, например, разрешены текстовые фрагменты пакетов данных общеупотребительных форматов, таких, как html, UTF-8, Json, xml. Любые скрипты должны безусловно удаляться из получаемых пакетов, также следует запретить прием файлов мультимедийных форматов, а, кроме того, просмотр и прослушивание файлов в онлайн режиме.
Автоматизация работы ученых советов
Наличие ученых советов нескольких категорий – неотъемлемая особенность научных организаций. Рассмотрим на примере Ученого совета возможность применения КСУ для автоматизации подразделений, типичных для научных организаций. Научные советы бывают различных категорий: диссертационные, научно-технические, ученый совет всей организации. Автоматизация работы таких подразделений имеет свои особенности как с точки зрения деловых процессов, так и обеспечения информационной безопасности. Для всех категорий советов характерны следующие особенности:
    • в них входят сотрудники различных подразделений;
    • в заседаниях советов участвуют не только сотрудники своей организации, но и приглашенные. Особенно это характерно для диссертационных советов, в заседаниях которых участвуют соискатели ученых степеней, оппоненты, приглашенные специалисты;
    • при работе советов рассматриваются разнообразные материалы, поступившие из внешних организаций;
    • результатом работы часто являются материалы, отправляемые в другие организации.
Оформление ученого совета, а особенно диссертационных советов, в качестве отдельного подразделения, позволяет существенно упростить процесс предоставления доступа его членам к необходимы материалам. При этом члены совета могут и не являться сотрудниками организации, этот случай должен специально обрабатываться на уровне администрирования КСУ. Такой порядок существенно упрощает процедуру получения и обработки документов ученым советом, поскольку доступ по дискреционной модели может быть предоставлен сразу всей группе пользователей, в которую входят члены ученого совета и технические сотрудники. 
По сложившейся практике и действующей нормативной базе допуск внешних сотрудников на заседания диссертационных советов происходит по отдельно составляемым спискам после проверки ряда необходимых документов. В случае, если приглашенные сотрудники будут работать с какими-либо АИС в организации, для них могут быть заведены учетные записи, а также предоставлен доступ к рабочим материалам. В данном случае наибольший интерес представляет реализация возможности создания временных учетных записей и предоставления временных прав на действия в системах, причем эти ограничения могут быть как по времени (для приглашенных на защиту внешних сотрудников и оппонентов), так и по какому-то условию (соискатель теряет права после отправки диссертационного дела в ВАК).
При подготовке результатов работы советов в электронном виде существенное значение имеет подтверждение их аутентичности, что обычно достигается применением усиленной (обычно квалифицированной) ЭП. При наличии в организации КСУ для этой цели можно использовать стандартный контроль целостности и простую ЭП. Усиленная подпись должна будет использоваться только при отправке информационных объектов из организации, когда они выйдут за пределы действия КСУ.
Заключение
Внедрение КСУ в ходе цифровизации деятельности научных организаций невозможно без надежного обеспечения информационной безопасности. Сложность этой задачи обусловлена тем, что в ходе ее решения требуется реализовать систему защиты данных не одной конкретной информационной системы, а программного комплекса, включающего все АИС, работающие в организации, а также КСУ, объединяющей все эти программные компоненты. В качестве решения поставленной задачи предлагается стандартизовать процесс обмена данными между АИС – ввести понятие информационного объекта КСУ, что позволит как обеспечить обмен данными между системами, так и реализовать ряд СЗИ: протоколирование, контроль целостности, управление доступом. В этом случае становится возможным полноценное внедрение простых и усиленных ЭП.
Внедрение КСУ позволяет изменить порядок администрирования всего программного обеспечения организации: сделать единую базу данных пользователей на основе базы данных домена, вести единый протокол безопасности, задавать права доступа ко всем обрабатываемым информационным объектам в терминах КСУ, что позволит автоматизировать управление доступом к объектам, передаваемым между различными АИС.
